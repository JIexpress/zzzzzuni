## 1. 先纠正一个认知：ZRender 现在不是「渲染管线」，是「旁路渲染器」

原生 C ABI（`Native/zplugin/zplugin.h`）当前导出 **62 个符号**，按功能分组如下：

| 组 | 导出 | 能做什么 |
|---|---|---|
| 版本/诊断 | `ZR_ApiVersion` `ZR_GetVersion` `ZR_GetBuildInfo` | 查版本 |
| 网格 | `ZR_MeshLoadFromMemory` `ZR_MeshStatsGet` `ZR_MeshFree` | 加载 .zmesh |
| 后端 | `ZR_SetBackend` `ZR_GetBackend` | D3D12 / Vulkan 二选一 |
| 超分 | `ZR_Upscaler_SetPreferred` `_GetActive` `_QueryCaps` | FSR/DLSS 设置与能力 |
| 插帧 | `ZR_FrameGen_InputBytesPerPixel` `_ValidateInputs` | 插帧入参校验 |
| Unity 桥·设备 | `ZR_Unity_AttachDevice` `_AttachDeviceFromTexture` `_DetachDevice` `_DebugGetAttachedDevice` | 接管 Unity 的 D3D12 设备 |
| Unity 桥·目标 | `ZR_Unity_CreateSharedTarget` `_GetSharedTargetHandle` `_GetSharedTargetResource` `_GetTargetStats` `_GetTargetResourceAt` `_GetReadableTargetIndex` `_GetSyncStats` `_ReadTargetPixels` `_ReleaseSharedTarget` `_RenderFrame` | 建共享纹理、渲染、读回 |
| Unity 桥·帧 | `ZR_Unity_BeginFrame` `_EndFrame` | 帧边界 |
| Unity 桥·场景 | `ZR_Unity_SetCamera` `_CreateMesh` `_DestroyMesh` `_DrawMesh` `_BeginScene` `_EndScene` `_GetSceneStats` | 提交网格 |

### 由此得出三条硬事实

| 事实 | 依据 |
|---|---|
| **它输出的是一张共享纹理，由 Unity 合成** | `CreateSharedTarget` / `GetSharedTargetResource` / `Unity_AttachDeviceFromTexture` 这一组 |
| **每个物体只有两样东西能交给它：一个 float 世界矩阵、一个 rgba** | `ZR_Unity_DrawMesh(handle, world16, rgba)` —— **没有材质、没有贴图、没有光照、没有实例化** |
| **相机只给两个 float 矩阵** | `ZR_Unity_SetCamera(float view16, float proj16)` —— **没有 double 原点、没有相机相对提交** |

**结论**：所谓"用 C++ 重写的渲染管线"，实际形态是**叠在 Unity 之上的旁路渲染器**——Unity 负责场景、材质、光照、剔除，ZRender 负责把 Unity 递过来的网格画进一张纹理，再做超分和后处理。

这不是缺陷，这是当前架构的真实形状。**但它决定了改进方向**，见 §2。

## 2. 关键抉择：不要把它做成完整管线

两条路，成本差一个数量级：

| 路 | 做法 | 要补的东西 | 成本量级 |
|---|---|---|---|
| A · 做成完整管线 | 替代 URP：自己管场景收集、剔除、材质、光照、阴影、GI | 材质系统、光照与阴影级联、实例化、双精度提交、剔除、光源数据…… | 等于重写半个引擎，年计 |
| **B · 做成专用通道**（建议） | 只做 Unity 做不了的那部分：**行星尺度的 chunk 渲染**，其余全交给 URP | 只补 §3 里 P2 那 4 项 ABI | 4–8 周 |

**选 B 的理由**：

1. URP 已经把"普通场景"做得够好，重做一遍没有收益
2. 这个项目的真实需求是「一颗 6371km 半径的星球，能走、能飞出去、能在太空看见」——这件事 Unity 确实做不了，而**原生侧已经有一半了**（`Native/tests/planet_math.h`：cube-sphere、fBm 高程、两档 LOD 迟滞、球面引力，15 条 doctest 全绿，6144 chunk / 640×480 / 7.9–8.8ms）
3. 走 B 的代价是"两套渲染共存"，而这个项目本来就要接受这件事

**判断标准**：如果一个改进项，URP 也能做，那就别在 ZRender 里做。

## 3. 四条改进线（按"挡不挡路"排）

### P0 · 一行修：FSR4 能力探测的假阴性 —— 0.5–1 天

**位置**：`Native/zupscaler/upscaler_caps.cpp:61`

```cpp
outCaps->fsr4Available = outCaps->fsrRuntimePresent && ZupFsr4Probe(nullptr);
```

**问题**：同一个函数上面几行**已经把真实适配器枚举出来了**，连 `vendorId` / `deviceId` 都读到了（见 `:46-56`），但传给 `ZupFsr4Probe` 的仍是 `nullptr`。

**后果**：设置页把 FSR 4.1 标成"（本机不支持）"，而硬件、运行时、引擎代码三层都支持。RX 9060 XT + SDK v2.3.0 实测：null 给 2 条，真设备给 4 条含 `4.1.2`。

**修法**：用已枚举到的适配器创建（或复用渲染线程的）`ID3D12Device`，传给 `ZupFsr4Probe`。

**完成判据**：
- `ZR_Upscaler_QueryCaps` 在有 RDNA4 的机器上返回 FSR4 可用
- 设置页不再显示"本机不支持"

**注意**：能力结果**进程内缓存**（首调触发一次探测），改完 DLL 必须**重启播放器**才看得到变化。

**验证方式**：探针（见 §5）在真设备上问一次，结果与 null 对照，两者不一致才算修好。

---

### P1 · 能力诚实化：让"不支持"能追溯到原因 —— 2–3 天

**现状**：`ZrUpscalerCaps` 只有一个布尔 `fsr4Available`。它无法区分三种情况：

| 情况 | 现在的表现 |
|---|---|
| 硬件不支持 | 都是 `false` |
| 运行时 DLL 缺失 | 都是 `false` |
| **根本没测**（探测输入错了） | 都是 `false` ← **这次踩的就是这个** |

**做法**：
1. 把 `upscaler_caps.cpp` 文件头与 `fsr_upscaler.cpp:131` 那两句"FFX 对 null 返回一致列表"的注释**改成事实**（实测证伪）
2. 给 `ZrUpscalerCaps` 加一个 `probeMode` 字段：`0 = 真实设备` / `1 = 保守回退` / `2 = 未探测`
3. 上层 UI 据此分三种文案：不支持 / 运行时缺失 / 未检测

**完成判据**：任何一次"不支持"都能说出是哪一类原因。

**为什么这条比 P0 值钱**：P0 修的是一个 bug，P1 修的是"以后所有 bug 都会伪装成不支持"这个机制。

### P2 · 专用通道：把行星从测试搬进生产 —— 4–8 周

**现状**：全部能力在 `Native/tests/planet_math.h` 与 `test_planet.cpp`，**生产库 0 引用**；`zplugin.h` 里没有任何 chunk / 双精度 / 重力接口。

**要扩的 ABI（核心工作量，就这 4 项）**：

| # | 扩什么 | 为什么 | 建议签名方向 |
|---|---|---|---|
| 1 | **double 相机位置** | 现在只有 float 矩阵；6371km 半径下 float 在 100km 处的 ULP 已经 7.8mm，抖动可见 | 增 `ZR_Unity_SetCameraOrigin(double x,y,z)`；矩阵仍 float，但改成相机相对 |
| 2 | **chunk 句柄 + double 变换** | 每块地形要在 double 空间定位，提交时转成相对相机的 float | `ZR_Planet_ChunkCreate(...)` / `_SetOrigin(handle, double x,y,z)` |
| 3 | **LOD 级别与邻居** | 两档 LOD 的接缝靠裙边遮蔽（不是消除），跨档要传邻居信息才能消缝 | `_SetLod(handle, level, neighborMask)` |
| 4 | **高度数据通道** | 现在 chunk 生成在原生侧，玩法侧拿不到地形高度（碰撞、放置都要） | `ZR_Planet_SampleHeight(double x,y,z, float* out)` |

**完成判据（缺一不可）**：

| 判据 | 测法 |
|---|---|
| 1080p 下 ≥30fps | 探针实测，不是估算（现有口径只有 640×480 / 7.9–8.8ms，**1080p 未验证**） |
| 地面 / 中空 / 轨道三档无可见接缝 | 同机位截图对比 |
| 跨 chunk 行走 1km 无跳变 | 位移前后像素差低于阈值 |
| 编辑器内、IL2CPP、Android | 三项现在**全部未验证**，先各测一次再谈优化 |

**不要顺手做的事**：不要因为改到这里了，就把 ZRender 往完整管线上推（见 §2）。

### P3 · 卫生项（按需，不挡路）

| 项 | 现状 | 处置 |
|---|---|---|
| 深度/不透明纹理 | `m_RequireDepthTexture:0` / `m_RequireOpaqueTexture:0` | 要做 SSAO / 软粒子前必须开；**开了有帧耗代价，先量再开** |
| RendererFeatures | 空 | 同上，与上一条一起做 |

| ZRender 桥在 Linear 下 | 用 `CreateExternalTexture(linear:true)`，画面比原生窗口直出略暗 | 记录为已知代价，不要为它再冒险 |
| 色彩空间 | 已迁 Linear，但 `m_LightsUseLinearIntensity` 随迁移翻 1，各场景未逐场景重标定 | **某场景偏亮/偏暗就调该场景 `Light.intensity`**，不做全局回调 |

## 4. 明确不建议做的四件

| 不做 | 理由 |
|---|---|
| 在原生侧自研刚体/约束求解器 | 等于自研物理，成本 > 收益；PhysX 的已知问题靠钳制质量比解决更便宜 |
| 全原生世界（双精度 + 自研物理 + 流式地形 + 大气散射） | 本阶段成本极高，属于"自研引擎" |
| 把 DataKernel 接进玩法 | 406M 行/s 的基准很好看，但玩法侧（几百个实体）根本用不上；它是人群 LOD 的备选，不是必需品 |
| 追 DLSS 5 真机 | 需要 RTX 50 系，本机没有。代码骨架留着即可 |

## 5. 需要新建的探针（不许用注释代替）

四个探针，每个都必须真跑、真输入、缺就报缺：

| 探针 | 问什么 | 输出 | 为什么必须有 |
|---|---|---|---|
| `fsr4-probe` | 这台机器的 FSR 4.1 到底支不支持 | 真实设备 / null 两条路径的能力条数对照 | P0 的唯一可信证据 |
| `planet-budget` | 1080p 下 chunk 数、帧耗、接缝计数 | 数字 + 截图 | 现有只有 640×480，1080p 未验证 |
| `abi-precision` | double → float 提交在 100m / 1km / 10km / 100km 的精度损失 | 各距离的 ULP（米） | P2 的验收依据；没有它，"没抖动"只是感觉 |
| `linear-bridge` | ZRender 输出与 URP 输出在同机位的亮度差 | 均值差、差值图 | 现在"略暗"是形容词，要变成一个数 |

**探针规矩**：拿不到数据时输出 `MISSING` + 原因，**不填 0、不填默认值、不写"暂无问题"**。

## 6. 验收口径：什么算"改进成功"

不看代码漂亮，看三条：

1. **每一个"不支持"都能说出原因**（P1 的产物：三态能力）
2. **至少有一组数字基线可对比**（1080p 帧耗、各距离精度损失、ZRender 与 URP 亮度差）
3. **第二章需要行星时，不用重新设计 ABI**（P2 的产物：double 原点 + chunk 句柄 + LOD 邻居 + 高度采样）

三条里第 3 条最重要——它是"现在做这些改进"的唯一理由。前两条是让第 3 条可信。

## 7. 与游戏侧的关系（供排期参考）

游戏第一版**不使用 ZRender 作为活跃管线**，用 URP。原因：C ABI 只能提交 float 变换 + rgba，第一版需要的是"一个舱外场景 + 一块盒子 + 一颗远景球"，URP 足够。

ZRender 真正被需要是**第二章**（行星地表）。所以这份计划的紧迫度是"第二章之前必须完成 P2"，而不是"现在就要"。

**但有一件事现在就该做**：留一条基线——用探针量出 URP 在"1 个舱外场景"里的帧耗并存档。没有基线，以后换管线也不知道是变好还是变坏。
