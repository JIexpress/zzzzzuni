
退出码：0 = JSON 已落盘；4 = 启动链/场景超时但仍写档（`status=aborted`）；3 = JSON 未写出。
不带任何开关时探针不创建对象、不写日志（实测 `Player.log` 里 `FrameBaseline` 0 次）。

**判据（本轮起生效，替代旧的"两两 p50 差 ≤5%"）**：同一指标**跑 3 轮取 p50 的中位数**，并同时给出 min / max 与包络 `(max−min)/median`。**两次对比的差超过包络，才算真变化**；落在包络内的一律视为噪声。包络随机器/构建/负载变化，换环境要重算。

## 4. 解读

### 4.1 为什么要 cost 口径

旧基线的 `cpuFrameTime p50=11.108ms` 恰好等于 90Hz 刷新间隔——**它只能证明"够 90fps"，证明不了"还剩多少"**。只要真实成本 < 11ms，帧间隔恒为 11.1ms，任何优化都测不出来。cost 口径去掉 vsync 等待后：

- 帧间隔 p50 掉到 **3.767ms（≈265fps）**——这才是这台机器跑这个场景的上限；
- 主线程 3.61ms、渲染线程 0.75ms、GPU 3.14ms → **瓶颈在 GPU（3.14ms）与主线程（3.61ms）之间**，两者接近，任一恶化都会先掉帧间隔；
- 相对 11.11ms 预算仍有约 **2.95×** 余量。

### 4.2 稳定性：cost 明显优于 asShipped

| 指标 p50 包络 | asShipped | cost |
|---|---|---|
| GPU | 5.75%（首版 4 轮 8.76%） | **1.31%** |
| 主线程 | 11.64%（首版 16.56%） | **2.67%** |
| 渲染线程 | 18.23%（首版 19.58%） | 10.16% |
| 帧间隔 | 0.01%（但那是 vsync 节拍，非成本） | 2.39% |

原因很直白：asShipped 的帧里 7–8ms 在等 vsync，等待被调度抖动切成大小不一的碎片，串到线程时间里就是 10–19% 的百分比噪声；cost 口径下线程连续工作，三次跑同一条流水线，包络收到 1–3%。

**结论：回归对比用 cost；asShipped 只用来回答"玩家实际看到什么"。**

### 4.3 p50 / p95 差距说明什么

- **cost 主线程**：p50 3.61ms → p95 4.77ms（+32%）→ p99 10.9–11.1ms。1% 的帧冲到 11ms，等于"这一帧被卡到 vsync 节拍"，来源是周期性任务（GC/物理/UI 重建一类）叠加。**p95/p99 是下一步要拆的对象**，p50 已经很稳。
- **cost GPU**：p50 3.14ms → p95 3.75ms（+19%）→ p99 4.65–8.49ms。稳态余量足，尾帧偶发 8ms。
- **cost 帧间隔的 p95 = 11.14ms 是个陷阱**：窗口模式下 DWM 合成仍按 90Hz 节拍，约 5% 的帧被合成器挡回 11.1ms——`vSyncCount=0` 去掉的是 **Unity 的** vsync 等待，不是桌面合成节拍。**cost 口径只用 p50 做回归判据，不要拿它的 p95 当"尾帧"读。**
- **asShipped**：p50≈p95≈p99（11.11/11.29/11.72）→ 抖动被 vsync 吸收在等待里，这条数字只能确认帧率上限。

## 5. 抖动归因（三查，实测）

| 查什么 | 结论 | 证据 |
|---|---|---|
| iGPU 是否被后台占用 | **有，且是常驻的**：采样期 `\GPU Engine(*)\Utilization Percentage` 上同时出现 player(pid 43968)、**dwm**(pid 1184, engtype_3d high priority)、**WorkBuddy**(pid 26948, engtype_3d)、System(pid 4, copy)；静置再测 WorkBuddy ≈ **7.1%** | 计数器实例名 + 进程名对照；见 `Docs/Logs/TASK-A-PERF-01.md` §2.4 |
| 是否插电 / 性能模式 | **插电**（`Win32_Battery.BatteryStatus=2`，电量 95%）；电源方案 = **平衡**（GUID `381b4222-f694-41f0-9685-ff5bb260df2e`），未开高性能 | `powercfg /getactivescheme` + WMI |
| 窗口是否失焦 | **未失焦**：5 轮（3 cost + 2 asShipped）全部 `focused=True`、`lostFocusFrames=0`；`runInBackground=1` | JSON `focus.*` |
| GPU p50 是否 >10% | **否，1.31%** → 三查未被触发；上面的记录是"顺手留证"，不是"已定位故障" | 3.1 表 |

结论：GPU p50 已经稳到可以做回归（1.31%）；剩下能看见的抖动在**渲染线程 p50（0.70–0.78ms，绝对差 0.04ms，包络 10.16%）**和**主线程 p95（4.33–4.82ms）**。渲染线程那 10% 的百分比噪声只有 0.04ms 的绝对值——低于这个量级的"优化"在这台机器上不可分辨。

## 6. 已知不代表性

1. **编辑器 ≠ 播放器**：本档是 release Player（Mono、非 Development Build、无 Profiler 附着）。编辑器 Play 多出 Editor 循环、场景视图、Profiler 采样，数字更高，**两边不可互换**；Development Build 打开 profiler 标记后开销也会变。
2. **无玩家输入**：采样期不动键鼠、相机不动。真实游玩有相机运动（视锥变化→可见物件/批次变化）、UI 刷新、交互逻辑。**本档是"出生点静止"的下界**。
3. **静态场景**：SCN_Game 是垂直切片出生点（Ground/Door/Pickup/Player/Enemy/NPC + 一盏方向光），无战斗/粒子/多目标。Triangles 逐轮 ±8 说明并非完全静止，但整体负载不代表后续内容。
4. **单机单会话**：一台 780M iGPU 机器、600 帧（cost 口径约 2.3 秒 / asShipped 约 6.7 秒），**不能外推到独显机或长时段热稳态**。
5. **cost 口径的边界**：`vSyncCount=0` 只去掉 Unity 的等待；窗口模式下 DWM 合成仍按 90Hz 节拍挡回部分帧（见 4.3）。要彻底排除合成器，得跑全屏独占——**本次没做**，做了必须另立口径。
6. **后台负载存在**：dwm 与 WorkBuddy（本代理宿主 UI，≈7% GPU）在采样期同占 iGPU，未关闭也未"清理"——这是本机的真实状态，记录而不粉饰。

## 回归判据（2026-11-15 验收修正，取代原「±0.04ms」）

- **有效门限 = ≥5 轮、跨 ≥2 个会话的中位数 ± 实测跨轮包络**：GPU ≈ **10%**、主线程 ≈ **12%**、渲染线程 ≈ **20%**、asShipped 帧间隔 ≈ **15%**。
- 单次三连跑的 1.31%（GPU）**不是**门限，只是同一时段离散度；拿它当门限会把正常漂移判成回归。
- **判回归的正确姿势**：改动前后各 5 轮，比中位数；差值 > 包络才算真变化；介于包络内就重跑，不许下结论。
- 已知未定位：冷启首轮 GPU 偏低（PSO 编译方向，未取证）、并发采集 GPU 计数器会自扰动（+7.4%），测量期不要并行采集。
